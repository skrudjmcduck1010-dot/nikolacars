# Почасовая очистка файлового кеша витрины

Команда `storefront:prune-expired-cache` обслуживает настроенный Laravel FileStore публичной витрины. Она доступна через Artisan. Единственные удаляемые файлы лежат в `storage/framework/cache/data/aa/bb/<sha1>`, имеют корректную структуру FileStore, принадлежат пользователю PHP, где доступен POSIX UID, и имеют одну жёсткую ссылку. Порог 48 часов применяется как к окончательному времени истечения, так и к последнему изменению. Временной запас отсчитывается после окончания интервала обслуживания устаревшего кеша.

Поддерживаются сериализованные массивы публичного ответа с ожидаемыми полями status/data и отдельные временные метки Cache::flexible. Для метки требуются целое UNIX-время, соответствие времени создания файла и известному TTL витрины в 300, 86 400 или 604 800 секунд, с допуском одной секунды между операциями Laravel. Строки владельца блокировки, произвольные числа и другие форматы пропускаются. Перед удалением команда захватывает неблокирующую файловую блокировку и повторно сравнивает имя с открытым inode. Содержимое кеша не десериализуется.

Один запуск просматривает до 4 096 из 65 536 шардов и до 6 000 файлов, удаляет до 2 000 записей. Мягкий предел прохода — 10 секунд между файловыми операциями. При почасовом расписании полный круг в лучшем случае занимает 16 часов, а предельная пропускная способность составляет 48 000 удалений за сутки. Нагрузка на файловую систему и количество кандидатов могут удлинить круг. В момент инцидента 2 ноября полная проверка наблюдала 9 392 недавно изменённых файла за двое суток. Это число включает перезапись, оно не измеряет скорость создания новых inodes.

Блокировка процесса, курсор и метрики последней успешной партии используют один файл `storage/framework/storefront-cache-prune.json`. Курсор сохраняет точный шард и позицию внутри него. Одновременный запуск завершается результатом `already_running`. Режим `--dry-run` показывает ближайшую партию, сохраняет файлы и не сдвигает курсор.

## Установка и проверка

Для выпуска передать только `app/Services/ExpiredStorefrontCache.php`, затем `app/Console/Commands/PruneStorefrontCache.php` штатным frontend-оператором с исходным SHA и подтверждением отсутствия новых путей. Сначала проверить, что в терминале аккаунта доступны указанный PHP CLI и nice, а установленная команда действительно видна в списке Artisan. PHP 8.3 размещался по указанному пути на этом аккаунте по предыдущей квитанции. Свежую доступность бинарника проверить до активации.

```sh
test -x /opt/alt/php83/usr/bin/php && test -x /usr/bin/nice
cd "$HOME/public_html/laravel_app" && /opt/alt/php83/usr/bin/php artisan storefront:prune-expired-cache --dry-run
```

Проверить текущие Cron Jobs владельца. При отсутствии существующей эквивалентной задачи добавить одну строку. Время старта — на 40-й минуте каждого часа по часам сервера. Правила cPanel, которые уже есть для склада или других приложений, сохраняются.

```cron
40 * * * * /usr/bin/nice -n 10 /opt/alt/php83/usr/bin/php "$HOME/public_html/laravel_app/artisan" storefront:prune-expired-cache > "$HOME/public_html/laravel_app/storage/logs/storefront-cache-prune-last.log" 2>&1
```

После сохранения перечитать установленную строку. После первого автоматического запуска проверить поля `completed_utc`, `inspected`, `removed`, `next_bucket` в состоянии и результат в `storage/logs/storefront-cache-prune-last.log`. Повторная запись перезаписывает один файл журнала. Фактическую динамику inodes проверить в cPanel. На сайте проверить новые сессии украинской и русской главных страниц. Для остановки удалить только установленную строку cron и проверить отсутствие следующего запуска. Для отката кода использовать проверенные материалы конкретного frontend-выпуска после остановки расписания. Истёкшие ответы заново формируются приложением при необходимости.
