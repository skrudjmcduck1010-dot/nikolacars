| `admin:refresh-sidebar-stats` | 12,27,42,57 | background | 10 минут |

Laravel собирает due events в начале каждого запуска. Foreground-команда
удерживает родителя до завершения. Mutex по умолчанию зависит от command и cron
expression, поэтому lock прогрева не блокирует feed или NP. Фактический live
cache store и состояние отдельных mutex этой проверкой не установлены.

`queue:work --max-time=50` проверяет время между заданиями. Это не жёсткий
50-секундный предел всего процесса, поэтому его наличие в следующую минуту
само по себе не доказывает ошибку.

Прогрев последовательно обновляет четыре snapshot: available/sold для uk/ru.
Свежесть 240 секунд, ограниченный last-good 900 секунд; revision может потребовать
раннего rebuild. Каждый snapshot имеет build lock 120 секунд. При занятом lock
фоновый refresh пропускается; неудачная сборка сохраняет last-good. В коде уже
есть лог `Storefront snapshot rebuilt.` с rows/duration_ms. Минутный запуск
не равнозначен четырём полным rebuild каждую минуту.

NP sync обходит заказы chunks по50, но синхронизирует их последовательно.
Общего временного бюджета команды в этом цикле нет. Это возможный источник
долгого foreground-родителя, но фактическая длительность не измерена.
Конфигурационные gates также влияют на фактический набор активных задач.

## Следующий план

Согласованная диагностика по доступным данным выполнена. Ниже предложения
для получения недостающих измерений; они не являются разрешением на выпуск.

1. **Уточнить источники, не запускать задачи.** Через разрешённое чтение сверить
   имена/размеры/mtime действующих и ротированных log-файлов и конфигурацию
   логирования, без вывода секретов. Подтвердить timezone приложения и snapshot.
   Это покажет, где искать события00:00–06:00 Kyiv и почему хвост laravel.log пуст
   по snapshot-метрикам. Отсутствие совпадений явно сохранять как ограничение.
2. **Расширить существующее чтение с пределом.** Для заранее выбранных файлов
   читать максимум1 MiB на файл, максимум3 файла за этап; выводить только
   нормализованное время, тип snapshot, rows, duration_ms и агрегаты count/p50/p95/max.
   Сначала проверить покрытие требуемого периода. Не выдавать сырой журнал,
   клиентские строки или произвольные context fields. Не повторять массовый crawl.
3. **Не вычислять NP/OLX duration из несопоставимых строк.** Проверить существующие
   start/end записи и однозначность пары command/process. Если подходящей
   телеметрии нет, следующим отдельным локальным изменением подготовить
   минимальные start/finish-метрики нужных Console Commands: фиксированное имя,
   process/run ID, монотонная длительность, итог; без заказов/ответов/секретов.
   Изолированная регрессия должна подтверждать отсутствие внешних операций.
   Выкладка такой диагностики — отдельный согласованный этап.
4. **Выбрать исправление по измерению.** Сопоставить законченные запуски с теми
   же окнами CPU/NPROC. Для snapshot отдельно проверить превышение120 s build lock
   и300 s scheduler lock. Для NP/OLX — число вызовов и ожидание. Для feed/cache —
   фактическую стоимость и одновременность сборок. Только затем готовить
   оптимизацию конкретной операции, сохраняя свежесть витрины, охват заказов,
   историю статусов, квитанции и порядок синхронизации.
5. **Проверить после отдельного разрешённого выпуска.** Сравнивать одинаковые
   временные окна, длительности, CPU/NPROC и ошибки витрины. Не путать app log
   exceptions с количеством публичных HTTP5xx. Нужны штатный release и rollback.
