# Чат сайта ↔ Telegram — возможность

31.10.2026, Europe/Kyiv. Статус: проверено по коду/документации; предложение, без реализации и активации.

Текущий bubble — Viber/Telegram deep links и callback, переписки внутри сайта нет. LeadController::callback отправляет Telegram sendMessage односторонне. Parts callback идёт через PartsCallbackController/SkladStorefrontClient в защищённый API склада, отдельный лид и notify-once receipt. Эти процессы сохраняются.

Поиск runtime/routes/dependency manifests/docs обоих проектов не обнаружил готового webchat-провайдера или входящего Telegram webhook/getUpdates. Другие односторонние Telegram-уведомления и темы групп существуют. Подключения в неизвестных аккаунтах этим поиском не проверены.

Последняя подтверждённая production-конфигурация сайта (docs/parts-storefront.md, 29.10): SQLite :memory:, file cache/sessions. Повторного live-чтения не было. Для истории чатов требуется постоянное хранилище: новая БД сайта либо отдельные chat-таблицы постоянного backend; склад автоматически не выбран. Cache не должен быть единственным хранилищем.

Предложенный первый вариант:

1. Клиент пишет в виджет без регистрации в Telegram; сервер сохраняет диалог и сообщение.
2. Отдельный бот отправляет сообщение в согласованную закрытую группу менеджеров.
3. Менеджер отвечает обычным Reply на сообщение бота. HTTPS webhook сопоставляет chat_id + reply_to_message.message_id с диалогом и сохраняет ответ.
4. Виджет периодически получает новые сообщения, пока открыт. Постоянный WebSocket-процесс для первого варианта не обязателен; его доступность на хостинге не проверена.

Несколько клиентов изолируются непрогнозируемыми session/dialogue tokens и сохранённым message-ID mapping. Неизвестный Reply не отправляется случайному клиенту. Для нескольких менеджеров — allowlist группы/user ID и сохранение автора ответа; назначение ответственного/темы на диалог возможны отдельно. Стартовый Reply-механизм не требует доступа бота ко всей переписке группы. Нельзя менять webhook действующего notification-бота без проверки других потребителей.

Нужны бот, получатели, HTTPS endpoint и постоянная история. Обязательны webhook secret, проверка отправителя, дедупликация update_id/client UUID, ограничения частоты/размера и безопасный доступ к диалогу. После сетевого timeout Telegram нельзя обещать exactly-once и слепо повторять отправку. Серверные токены не попадают в браузер.

При закрытой вкладке ответ сохраняется до возврата в ту же сессию; уведомить анонимного клиента вне сайта без отдельного канала нельзя. История на другом устройстве требует идентификации. График/офлайн-текст можно использовать существующий. Файлы/фото и автоматическое создание CRM-лидов — отдельный scope.

Root проверил официальные [Telegram Bot API](https://core.telegram.org/bots/api) и [Bot FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get): sendMessage/setWebhook и ответы на сообщения бота при privacy mode позволяют такой мост. Существующий notification-бот ещё не настроен для этого потока.

Для Viber также нужен API-бот, обычная ссылка viber://chat недостаточна. По [Viber REST Bot API](https://developers.viber.com/docs/api/rest-bot-api/) новые боты с 05.02.2024 создаются на коммерческих условиях. Условия конкретного аккаунта/стоимость не запрашивались. Для старта предложен Telegram.

Проверены AGENTS обоих проектов, карта склада, история integrations_orders, parts-storefront, актуальная callback-документация и соответствующий код. Env/секреты/клиентские данные не читались; отправок, новых ботов, runtime/DB/config/webhook/live изменений, зависимостей и расписаний не было. Это документальная оценка, runtime-тесты не запускались.

Следующий шаг перед реализацией: определить чат разборки или всего сайта, одного менеджера или группу, ответственных и место хранения. Затем ограниченный implementation scope и изолированные проверки двух клиентов/Reply/duplicate webhook/возврата вкладки; активация отдельно. План не разрешает отправки/публикацию. Откат текущей работы — удалить только этот отчёт и добавленную тематическую запись.

Уточнение 31.10.2026, Europe/Kyiv: владелец выбрал для Telegram один личный чат менеджера с ботом на всех клиентов; группа из предложения выше не обязательна. Для Viber аналогичный единый чат организуется ботом с клавиатурой «Ответить клиенту №…»/выбором активного диалога и сохранением соответствия на backend; клиент остаётся на сайте, отдельные личные чаты с каждым посетителем автоматически не создаются.
В Viber REST API message callback не документирован Telegram-подобный reply_to_message, поэтому обычную цитату нельзя обещать как механизм маршрутизации. Это уточнение предложения, без runtime/настроек/отправок; root отдельно проверяет официальный Viber API, коммерческие условия новых ботов остаются применимы.
