## Подготовленный scope

Новые **82 уникальных правила**, считая модель и путь, устраняют подтверждённые дубли. Точный состав: [alias map](canonical-63-2026-11-21-sources/new-aliases.json). Это 39 новых двуязычных групп, дополнительные проверенные батарейные уровни и одно исключение RU Wi-Fi. Одинаковый UA/RU slug педали хранится одним правилом. Существующие parent→leaf направления сохранены; обратные правила и цепи не добавлены. Проверен инвариант `preferred(target) = target`.

Production payload — ровно четыре runtime-файла:

- `app/Services/CatalogPath.php` — scoped карта, выбор раскрытого источника и точечные языковые исключения Wi-Fi.
- `app/Services/CatalogNavigation.php` — слияние одинаковых конечных ссылок с сохранением доступных потомков.
- `app/Http/Controllers/PartsController.php` — одинаковая подготовка SSR/AJAX query и корректные языковые связи.
- `resources/views/layouts/parts.blade.php` — не выводить ложный RU hreflang у двух UA Wi-Fi листьев.

Тест, fixture и runner не входят в production payload. Query, включая page, поиск, сортировку и click IDs, сохраняются через 301. Локаль, модель и товарные ID стабильны. Общего схлопывания повторных сегментов нет.

### Навигация и один upstream-запрос

Склад отдаёт только раскрытую ветку. У приборной панели исходный root payload содержит root и одинаковый child, а третьи уровни появляются только при выборе child. Простое удаление child из меню делало бы их недоступными.

Теперь canonical parent получает payload доказанного эквивалентного child **одним запросом**, до вычисления cache key. При нескольких объединённых уровнях выбирается самый глубокий direct source. URL и canonical остаются у parent. SSR и AJAX используют один helper; дополнительных запросов на каждую страницу нет. Объединённые строки показывают стрелку только при оставшихся distinct потомках. Нераскрытые посторонние ветки сохраняют upstream-флаг. JS использует тот же готовый `navigation` и экспортированную preferred map.

Точные более глубокие URL остаются самостоятельными. Sitemap по прежней политике содержит верхние разделы и товары; новые deep aliases в него не добавляются. Общего cache flush, изменения TTL, складского API или бизнес-данных нет.

Использован `per_page=100`; для малых полных листингов повторный запрос заменён уже прочитанным HTML payload. Сохранены [170 API-наблюдений](canonical-63-2026-11-21-sources/api-observations.json). Дополнительно выполнены 12 первых panel-чтений, шесть батарейных root-чтений и одно чтение смешанного UA Wi-Fi slug. Никаких форм, заказов, SQL-записей или клиентских отправок нет.

### Wi-Fi: две UA категории и один RU slug

UA parent содержит 10 товаров, распределённых между двумя листьями: `antena-wi-fi/antena-wi-fi` — 7 и `antena-wi-fi/antenna-wi-fi` — 3. RU parent и leaf содержат все 10.

Read-only анализ склада выявил причину: `StorefrontCatalogTaxonomy::sectionSlug()` превращает «Антенна Wi-Fi» и «Антенна - Wi-Fi» в одинаковый `antenna-wi-fi`. `StorefrontCatalogQuery` и `StorefrontCategoryNavigation` фильтруют и группируют по локализованным путям. Языковая ссылка выбирается по первой товарной строке, поэтому RU листинг из 10 товаров указывал на UA листинг из 7. Изолированная проверка `Str::slug` воспроизвела коллизию. Числовые category ID публичный контракт не отдаёт; live DB не читалась, ID не выдумывались. Складские исходники, таксономия и товары не менялись.

Узкое frontend-исправление:

- Только RU leaf перенаправляется на равный ему RU parent из 10 товаров.
- RU parent и UA parent из 10 товаров имеют взаимные hreflang.
- Два отдельных UA листинга сохраняют 200, собственный canonical, UK и x-default. Ложная ссылка RU alternate исключена.
- Кнопка переключения языка у UA листьев ведёт на общий RU parent: раздельного RU эквивалента в текущем API нет.

Уникальность backend slugs/ID и карта их совместимых URL остаются отдельным возможным улучшением. Это не разрешение менять категории или складские данные в текущей задаче.

### Батареи

[Шесть root-проверок](canonical-63-2026-11-21-sources/battery-root-inventories.json) подтвердили:

- Model Y и Model S 2012–2016: root, второй и третий уровни имеют по 3 одинаковых ID в UA/RU. Оба deep URL направляются прямо на root; раскрытие получает самый глубокий payload.
- Model 3: root содержит 4 ID, внутренние уровни — по 3. Root включает другую подветку электрических компонентов и остаётся самостоятельным. Объединяются только равные внутренние второй/третий уровни.

### Сиденья Highland и старые категории

У сидений второго ряда Highland parent содержит 5 ID, leaf — 2 в обеих локалях. Адреса #51/#53 не объединяются. Сохранённая RU инспекция Google от 3 октября одновременно показывает старую причину canonical conflict и Google canonical, совпадающий с пользовательским. Текущий выбор parent этим не подтверждён.

Для широких разделов #59/#63 Google сохранил сентябрьские `/parts/category/.../` URL. Сейчас оба старых адреса дают прямой 301 на соответствующие новые разделы с 200/self-canonical. Объединять широкие разделы с одной из подкатегорий нельзя. [Проверки старых alias](canonical-63-2026-11-21-sources/legacy-category-targets.json).
