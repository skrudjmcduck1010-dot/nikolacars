## Что означают предупреждения по коду

### Новая почта

`AdminOperationsHealthService::novaPoshtaCheck()` читает сохранённые записи
отправлений. Просрочкой считается пустой `np_status_checked_at` либо отметка
**строго раньше now−30минут**; порог конфигурируется с нижней границей10минут.
Рабочее расписание — :08/:18/:28/:38/:48/:58 Europe/Kyiv с mutex15минут.

Активная выборка уже использует `CustomerOrderShipment::needsScheduledStatusCheck()`:
полученные основные ТТН с кодом9 исключены, кроме незавершённых сохранённых
возвратов/связанных документов. Фильтр заказа сохраняет активные статусы и
недавно выданные заказы, исключает возвращённые на склад. Новая выборка
одинаково применяется к health и плановой синхронизации.

«Просрочена проверка» означает возраст последнего сохранённого опроса;
это не доказательство проблемы с самой доставкой. Исключение одного основного
API-запроса ловится в `syncPending()`: обход продолжает другие заказы,
а проблемная отметка не обновляется. Команда может завершиться успешно при
`failed > 0`. `recentErrors` в health отдельно считает сохранённые
`error_message` за сутки; ноль таких строк не доказывает отсутствие исключений
опроса, которые уже отражены в выделенных метриках.

Обычное боковое меню читает готовую health-сводку с максимальным возрастом
600секунд; scheduler обновляет её каждые5минут. Если предупреждение взято
из этой сводки, оно может отставать от БД. Открытие страницы health пересчитывает
основные проверки и сохраняет диагностический кеш, но само не запускает NP sync.

### Laravel Scheduler и кеш

`SchedulerHeartbeatService::status()` использует **filemtime** файла
`storage/app/operations/scheduler-heartbeat.json`, а не timestamp внутри JSON.
Сигнал свежий при `age_seconds <= max_age_seconds`; показанный порог180секунд.
`humanDuration()` округляет минуты вниз. Поэтому надпись «3мин» может означать
181–239секунд и корректно сопровождаться предупреждением при пороге180.

Heartbeat зарегистрирован ближе к концу расписания. Предшествующие foreground
задачи могут задержать его выполнение; это объяснение возможного механизма,
а не доказанная причина конкретного сообщения владельца. Свежий `up` показывает,
что сигнал сейчас снова проходил допустимый порог; менять cron на этом основании
не требуется.

Общий текст рекомендации о планировщике и хранилище кеша не является результатом
измерения неисправности cache storage. В `OperationsHealthExplanation` есть
отдельная проверка `cache` и общий fallback-текст о диагностике. Чтобы утверждать
сбой кеша, нужен её конкретный результат или соответствующая ошибка журнала.
Ни сообщения «3мин», ни текущего `up` для такого вывода недостаточно.

POST и запускает синхронизацию; она не нужна для read-only идентификации.

Для heartbeat достаточно чтения mtime без приложения, например через IAB Terminal:

```bash
/opt/alt/php83/usr/bin/php -r '$p="/home/nikolaca/sklad_app/storage/app/operations/scheduler-heartbeat.json"; $m=is_file($p)?filemtime($p):false; echo json_encode(["observed_utc"=>gmdate("c"),"mtime_utc"=>$m===false?null:gmdate("c",$m),"age_seconds"=>$m===false?null:max(0,time()-$m)],JSON_UNESCAPED_SLASHES).PHP_EOL;'
```

На свежей health восстановление уже зафиксировано. При повторном предупреждении
сначала установить точную ошибку по метрикам. До этого не менять частоты,
